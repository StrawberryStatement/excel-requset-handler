# 需求回填动作执行说明

## 1. 定位

本文说明需求对齐完成后的具体执行动作，包括 Excel 回填、RR-FE 映射回填、待回刷评论清单生成、线上系统评论写入和闭环验证。

本文不替代 [需求管理运作规范](./需求管理运作规范.md)。运作规范负责定义团队应该如何管理需求、谁负责确认、什么条件算合规；本文负责定义在合规结论已经形成后，工具和执行人如何把结论回填到表格或线上系统。

边界：

1. 运作规范决定“是否应该沉淀”。
2. 回填动作决定“如何执行沉淀”。
3. 回填动作不能绕过运作规范中的准入、禁止和遵从性要求。
4. 当前阶段线上系统只写评论，不直接更新状态、排期、负责人等结构化字段。

## 2. 回填动作分类

| 动作 | 触发条件 | 执行对象 | 主责人 | 输出 |
| --- | --- | --- | --- | --- |
| Excel 映射回填 | RR 已创建、FE 已创建或 RR-FE 关系已确认 | 来源列表、待建 FE 清单、待创建 RR 清单 | 产品经理 | 更新后的编号映射和处理状态。 |
| 待回刷评论生成 | 对齐结论已确认，且满足线上沉淀准入 | 工具导出的待回刷评论清单 | 产品经理 | 待回刷评论清单。 |
| 线上评论回刷 | 待回刷评论清单通过人工确认 | 线上系统 FE 或 RR | 产品经理或系统执行人 | 线上系统评论记录。 |
| 回刷结果校验 | 评论回刷完成后 | 线上系统和下一轮基准表 | 产品经理 | 成功记录、失败记录、待重试记录。 |

## 3. 总体动作流程

```mermaid
flowchart TD
  A["接收线上沉淀输入清单<br/>来自运作规范流程"] --> B{"是否满足回填前置条件"}
  B -- "否" --> C["退回规范流程<br/>补充主键、云服务、责任人或确认结论"]
  B -- "是" --> D["生成回填任务<br/>映射回填、评论生成、线上写入"]
  D --> E{"是否需要补 RR 或 FE"}
  E -- "是" --> F["执行编号创建后的表格回填<br/>补 RR、补 FE、补 RR-FE 映射"]
  F --> G["重新导入分析<br/>验证映射是否生效"]
  E -- "否" --> H["生成待回刷评论清单"]
  G --> H
  H --> I{"人工确认评论清单"}
  I -- "否" --> J["修改评论内容或排除记录"]
  J --> H
  I -- "是" --> K["调用线上系统接口或人工录入评论"]
  K --> L{"回刷是否成功"}
  L -- "否" --> M["记录失败原因<br/>进入待重试清单"]
  M --> K
  L -- "是" --> N["记录回刷结果<br/>等待下一轮基准验证"]
```

## 4. 回填前置条件

执行任何回填动作前，必须满足以下条件：

| 条件 | 要求 | 不满足时处理 |
| --- | --- | --- |
| 主键明确 | 至少有 FE编号 或 RR编号 | 退回补充主键；无法补充时不回填。 |
| 云服务明确 | 需求必须有云服务 | 补充云服务或使用显式默认值填充。 |
| 结论已确认 | 结论经过产品经理和相关责任人确认 | 退回对齐流程。 |
| 责任人明确 | 风险、下一步动作、依赖服务计划必须有责任人 | 补充责任人后再执行。 |
| 目标对象明确 | 明确写 FE、RR，或写当前对象加一层关联对象 | 未确认时默认只写当前对象。 |
| 异常已处理 | 不存在阻断类异常 | 先处理异常，不执行回填。 |

## 5. Excel 映射回填动作

### 5.1 适用场景

Excel 映射回填用于把新创建或新确认的编号关系补回表格，使下一次分析能够稳定关联。

适用场景：

1. `RR编号` 有值但 `FE编号` 为空，内部已经创建 FE。
2. 外部诉求已经创建 RR，需要把 RR 补回来源列表。
3. 一个 RR 拆成多个 FE，需要明确 RR-FE 拆分关系。
4. 多个 RR 合并到一个 FE，需要明确多个 RR 和同一个 FE 的关系。
5. 工具识别到 FE 候选，人工确认后需要补齐映射。

### 5.2 回填字段

| 字段 | 是否必填 | 说明 |
| --- | --- | --- |
| 来源列表 | 必填 | 原始文件名，用于定位来源。 |
| 来源行号 | 必填 | 原始 Excel 行号。 |
| 云服务 | 必填 | 用于辅助确认服务归属。 |
| RR编号 | 条件必填 | 外部需求编号。外部诉求必须填写。 |
| FE编号 | 条件必填 | 内部交付编号。进入研发排期必须填写。 |
| 处理状态 | 必填 | 待创建RR、待建FE、已回填、无需创建、待确认。 |
| 处理说明 | 建议填写 | 说明为什么创建或不创建。 |

### 5.3 执行规则

1. 回填前必须保留原始来源文件，不覆盖原始数据。
2. 回填后的映射应生成新的处理结果文件或导入回工具，不建议直接覆盖项目经理原始文件。
3. 回填完成后必须重新导入分析，确认异常项已消除。
4. 如果回填后仍出现 RR 关联异常或云服务冲突，应退回运作规范流程重新确认。
5. 回填映射只解决编号关系，不代表状态、排期或风险已经确认。

## 6. 待回刷评论生成动作

### 6.1 输入

待回刷评论生成依赖以下输入：

1. 线上沉淀输入清单。
2. 评论目标：FE、RR，或当前对象加一层关联对象。
3. 评论字段配置，例如对齐结论、会议纪要、风险、客户影响、备注。
4. 评论模板。
5. FE/RR 关联关系。

### 6.2 评论内容要求

评论必须能说明：

1. 这条结论来自哪个来源列表或哪次对齐。
2. 结论适用于哪个 FE 或 RR。
3. 当前确认了什么状态、排期、风险或下一步动作。
4. 谁需要继续跟进。
5. 如果涉及依赖服务，依赖服务是否已经确认。

默认评论结构建议：

```text
【需求对齐结论】
来源：{{来源列表}}
云服务：{{云服务}}
关联FE：{{FE编号}}
关联RR：{{RR编号}}

【确认结论】
{{对齐结论}}

【补充信息】
排期：{{排期}}
风险：{{风险}}
会议纪要：{{会议纪要}}
下一步责任人：{{下一步责任人}}

【说明】
本评论基于已确认的需求对齐结论生成，用于线上系统留痕。
```

### 6.3 人工确认规则

待回刷评论清单生成后，必须人工确认以下内容：

| 确认项 | 要求 |
| --- | --- |
| 目标对象 | FE/RR 编号正确，不写错对象。 |
| 评论内容 | 不包含未确认承诺，不包含临时口径。 |
| 关联同步 | 只同步一层关联对象，不递归扩散。 |
| 依赖服务 | 未确认依赖服务计划时，不写成已承诺。 |
| 排除项 | 存在争议或异常的记录应排除。 |

## 7. 线上系统评论回刷动作

### 7.1 执行方式

线上系统评论回刷支持三种执行方式：

| 方式 | 适用阶段 | 说明 |
| --- | --- | --- |
| 人工录入 | MVP 或接口未接通阶段 | 用户根据待回刷清单手工复制评论到线上系统。 |
| 本地 MCP server 调用 | 推荐的内网自动回刷方式 | 本工具后端调用本机 MCP server，由 MCP server 访问内部系统并完成 FE/RR 评论回刷。 |
| 直接 API 调用 | 只有不使用 MCP server 时才考虑 | 由预留接口模块根据 FE/RR 直接调用线上系统评论 API。 |

推荐优先使用本地 MCP server。接口模块应独立维护，不应和 Excel 分析逻辑强耦合。后续内部模型或内部系统适配时，优先修改接口适配模块。

### 7.2 推荐架构：前端 HTTP 接口不变，后端适配 MCP

如果内网回刷通过本地 MCP server 完成，不建议让浏览器前端直接调用 MCP server。推荐架构如下：

```mermaid
flowchart LR
  A["前端按钮<br/>回刷评论到 FE"] --> B["FastAPI<br/>POST /api/fe-comments"]
  B --> C["internal_system.py<br/>内部系统适配器"]
  C --> D["本地 MCP server<br/>内部系统工具"]
  D --> E["内部需求管理系统<br/>FE/RR 评论"]
```

这样拆分的原因：

1. 前端仍然只访问本工具后端，不需要知道 MCP server 的启动方式、鉴权方式和工具名。
2. `backend/app/main.py` 继续负责参数校验和中文错误响应。
3. `backend/app/integrations/internal_system.py` 负责把 `add_comment(fe_id, comment)` 翻译成 MCP tool 调用。
4. 本地 MCP server 负责真正访问内部系统，处理内网鉴权、接口字段、错误码和审计。

结论：

| 层级 | 是否需要改接口 | 说明 |
| --- | --- | --- |
| 前端页面 | 不建议改 | 继续调用 `/api/fe-comments`。 |
| FastAPI 对前端接口 | 不建议改 | 保持 `fe_id + comment` 的稳定入参。 |
| 后端内部适配接口 | 需要改实现 | `internal_system.py` 从 dry-run 改为 MCP client。 |
| MCP server tool 接口 | 需要定义清楚 | MCP server 需要暴露 FE/RR 查询和评论写入工具。 |
| Excel 分析流程 | 不需要改 | `v2_workflow.py` 不应依赖 MCP。 |

### 7.3 内网替换文件清单

后续把代码带到内网后，其他模型或开发同学应优先看本节。真实线上系统回刷能力只应替换接口适配层，不应改 Excel 分析主流程。

| 文件 | 是否必须改 | 改造目的 | 说明 |
| --- | --- | --- | --- |
| `backend/app/integrations/internal_system.py` | 必须 | 接入本地 MCP server | 这是 FE/RR 查询和评论写入的主替换入口。真实回刷逻辑应写在这里，而不是写进 Excel 分析流程。 |
| `backend/app/main.py` | 按需 | 把 dry-run client 切换为 MCP client | 当前 `/api/fe-comments` 使用 `DryRunInternalSystemClient`。内网可切换为 `McpInternalSystemClient` 或 `InternalSystemClient` 的 MCP 实现。 |
| `backend/app/commenting/template_engine.py` | 一般不改 | 生成评论文本 | 只有评论模板变量规则变化时才改。 |
| `backend/app/services/v2_workflow.py` | 一般不改 | Excel 分析、FE/RR 关联、待回刷清单生成 | 不建议为了接 API 修改这里，避免把内部系统逻辑耦合进 Excel 分析。 |
| `frontend/app.js` | 按需 | 页面按钮和接口调用 | 如果后端接口路径、返回结构、确认流程变化，再改这里。 |
| MCP server 项目 | 必须 | 实现内部系统 tool | MCP server 不一定在本仓库内，但必须能被本工具后端调用。 |
| `docs/需求回填动作执行说明.md` | 按需 | 记录内网实现差异 | 内网适配后应补充 MCP server 启动方式、tool 名称、鉴权方式和错误码。 |

推荐替换优先级：

1. 先确认本地 MCP server 能独立完成 FE/RR 查询和评论写入。
2. 再改 `backend/app/integrations/internal_system.py`，实现 MCP client 调用。
3. 再改 `backend/app/main.py`，让 `/api/fe-comments` 使用 MCP client。
4. 最后按需改 `frontend/app.js`，补充用户确认、失败重试或执行结果展示。

### 7.4 `internal_system.py` 替换说明

`backend/app/integrations/internal_system.py` 是内部系统适配器文件。内网模型应在这个文件中实现 MCP client 逻辑。

必须保留的方法语义：

| 方法 | 入参 | 出参 | 用途 |
| --- | --- | --- | --- |
| `get_feature(fe_id: str)` | FE 编号 | `InternalFeature` | 按 FE 查询线上对象是否存在。 |
| `add_comment(fe_id: str, comment: str)` | FE 编号、评论内容 | `dict` | 给 FE 写入评论。 |
| `get_requirement(rr_id: str)` | RR 编号 | `dict` | 按 RR 查询线上对象是否存在。 |
| `add_requirement_comment(rr_id: str, comment: str)` | RR 编号、评论内容 | `dict` | 给 RR 写入评论。 |

当前 MVP 中的 `DryRunInternalSystemClient` 只用于本地演示，不会调用真实系统。内网替换时可以保留 dry-run 类用于测试，但生产路径必须使用 MCP client。

建议真实实现保持以下结构，类名可以按内网实际情况调整：

```python
class McpInternalSystemClient(InternalSystemClient):
    def __init__(self, server_url: str | None = None, command: str | None = None) -> None:
        self.server_url = server_url
        self.command = command

    def get_feature(self, fe_id: str) -> InternalFeature:
        # TODO: 调用本地 MCP tool：按 FE 查询
        ...

    def add_comment(self, fe_id: str, comment: str) -> dict:
        # TODO: 调用本地 MCP tool：给 FE 添加评论
        ...

    def get_requirement(self, rr_id: str) -> dict:
        # TODO: 调用本地 MCP tool：按 RR 查询
        ...

    def add_requirement_comment(self, rr_id: str, comment: str) -> dict:
        # TODO: 调用本地 MCP tool：给 RR 添加评论
        ...
```

MCP client 的返回值建议统一为字典，至少包含：

| 字段 | 说明 |
| --- | --- |
| `success` | 是否成功。 |
| `target_type` | `FE` 或 `RR`。 |
| `target_id` | FE 编号或 RR 编号。 |
| `comment_id` | 内部系统返回的评论 ID，没有则为空。 |
| `message` | 成功或失败说明，必须是中文或可展示给用户的文本。 |
| `raw` | MCP tool 原始返回，可选，用于排查问题。 |

### 7.5 MCP server tool 契约建议

本地 MCP server 至少需要暴露以下工具。工具名可以不同，但必须在文档或配置中明确映射。

| 建议 tool 名 | 入参 | 出参 | 用途 |
| --- | --- | --- | --- |
| `get_feature` | `{"fe_id": "FE-xxx"}` | FE 对象或不存在错误 | 校验 FE 是否存在。 |
| `add_feature_comment` | `{"fe_id": "FE-xxx", "comment": "..."}` | 评论写入结果 | 给 FE 添加评论。 |
| `get_requirement` | `{"rr_id": "RR-xxx"}` | RR 对象或不存在错误 | 校验 RR 是否存在。 |
| `add_requirement_comment` | `{"rr_id": "RR-xxx", "comment": "..."}` | 评论写入结果 | 给 RR 添加评论。 |

MCP tool 返回结果建议保持稳定：

```json
{
  "success": true,
  "target_type": "FE",
  "target_id": "FE-1001",
  "comment_id": "comment-123",
  "message": "评论写入成功",
  "raw": {}
}
```

失败时也必须返回结构化信息，不能只返回异常字符串：

```json
{
  "success": false,
  "target_type": "FE",
  "target_id": "FE-1001",
  "error_code": "FEATURE_NOT_FOUND",
  "message": "未找到对应 FE，请确认 FE 编号是否正确",
  "raw": {}
}
```

### 7.6 MCP 配置建议

内网适配时建议通过环境变量或配置文件声明 MCP server，而不是把命令、URL、token 写死在代码里。

建议配置项：

| 配置项 | 示例 | 说明 |
| --- | --- | --- |
| `INTERNAL_SYSTEM_WRITEBACK_MODE` | `mcp` | 可选值建议：`dry_run`、`mcp`、`direct_api`。 |
| `INTERNAL_SYSTEM_MCP_TRANSPORT` | `stdio` 或 `http` | MCP server 通信方式。 |
| `INTERNAL_SYSTEM_MCP_COMMAND` | `python path/to/server.py` | stdio 模式下的启动命令。 |
| `INTERNAL_SYSTEM_MCP_URL` | `http://127.0.0.1:xxxx/mcp` | http 模式下的 server 地址。 |
| `INTERNAL_SYSTEM_MCP_TOOL_ADD_FE_COMMENT` | `add_feature_comment` | FE 评论写入 tool 名称。 |
| `INTERNAL_SYSTEM_MCP_TOOL_ADD_RR_COMMENT` | `add_requirement_comment` | RR 评论写入 tool 名称。 |

如果内网 MCP server 已由其他进程统一启动，本工具只需要配置 MCP server 地址或连接方式。

### 7.7 `main.py` 切换点

当前 FE 评论按钮调用后端接口：

```text
POST /api/fe-comments
```

这个接口位于：

```text
backend/app/main.py
```

当前代码使用：

```python
DryRunInternalSystemClient().add_comment(fe_id, comment)
```

内网使用 MCP server 时，应改为类似：

```python
client = McpInternalSystemClient(
    server_url=os.getenv("INTERNAL_SYSTEM_MCP_URL"),
    command=os.getenv("INTERNAL_SYSTEM_MCP_COMMAND"),
)
result = client.add_comment(fe_id, comment)
```

建议不要在 `main.py` 中直接写复杂请求逻辑。`main.py` 只负责：

1. 校验前端传入的 FE 编号和评论内容。
2. 调用 `InternalSystemClient` 或 `McpInternalSystemClient`。
3. 把成功、失败、无权限、对象不存在、MCP server 不可用、接口超时等结果转成前端可读的中文响应。

### 7.8 不建议修改的文件

为了让其他模型更容易识别边界，以下文件默认不要因为“接真实回刷 API”而修改：

| 文件 | 不建议修改原因 |
| --- | --- |
| `backend/app/services/excel_io.py` | 只负责 Excel 读取导出，和内部系统 API 无关。 |
| `backend/app/services/v2_workflow.py` | 只负责关联分析和清单生成，不应直接依赖内部系统。 |
| `backend/app/commenting/extractors.py` | 只负责从文本中提取时间、人员等变量。 |
| `backend/app/commenting/template_engine.py` | 只负责渲染评论模板。除非模板变量规则变化，否则不要改。 |
| `frontend/styles.css` | 接 API 通常不需要改样式。 |

### 7.9 内网适配完成后的验证要求

内网真实回刷能力完成后，至少验证以下场景：

1. FE 存在，评论写入成功。
2. FE 不存在，返回中文错误，前端能提示“对象不存在”。
3. token 失效或无权限，返回中文错误，前端能提示“无权限或登录失效”。
4. 内部系统接口超时，返回中文错误，并保留待重试状态。
5. 同一条评论不会因为重复点击被重复写入，或至少能在前端给出重复提交提示。
6. dry-run 模式仍可用于本地测试，不依赖内网。
7. MCP server 未启动或 tool 不存在时，前端能提示“本地回刷服务不可用”。
8. MCP tool 返回失败时，后端能保留 `error_code` 和中文 `message`。

### 7.10 API / MCP 模块建议边界

建议后续内部适配时保留以下边界：

| 模块 | 职责 |
| --- | --- |
| Excel 分析模块 | 负责读取 Excel、识别差异、生成沉淀输入。 |
| 评论生成模块 | 负责按模板生成待回刷评论。 |
| 线上系统适配模块 | 负责调用本地 MCP server，查询 FE/RR、写评论、返回执行结果。 |
| 执行审计模块 | 负责记录成功、失败、重试、跳过原因。 |

线上系统适配模块至少需要支持：

1. 按 FE编号 查询线上对象。
2. 按 RR编号 查询线上对象。
3. 给 FE 添加评论。
4. 给 RR 添加评论。
5. 返回成功、失败、对象不存在、无权限、接口超时等结果。

## 8. 回刷结果校验

回刷完成后必须进行校验。

| 校验项 | 要求 | 失败处理 |
| --- | --- | --- |
| 对象存在 | FE/RR 在线上系统中存在 | 记录对象不存在，退回确认编号。 |
| 评论写入成功 | 线上系统返回成功或人工确认已写入 | 进入待重试清单。 |
| 评论内容一致 | 写入内容与待回刷清单一致 | 修正后重新写入或追加更正说明。 |
| 关联对象处理正确 | 只写当前对象或一层关联对象 | 如写错对象，必须记录并人工更正。 |
| 下一轮基准可追溯 | 下一次导出时能看到评论或关联结果 | 排查接口失败、权限或导出范围问题。 |

## 9. 禁止动作

以下动作禁止执行：

1. 未经人工确认，直接把工具识别结果写入线上系统。
2. 在存在主键缺失、云服务冲突、依赖服务未确认时写入承诺性评论。
3. 直接覆盖项目经理原始 Excel 文件且不保留原始版本。
4. 把临时会议意见写成最终承诺。
5. 递归同步关联对象，导致评论扩散到多层 FE/RR。
6. 在 MVP 阶段直接更新线上系统结构化字段。

## 10. 与运作规范的关系

执行顺序必须是：

1. 先按需求管理运作规范完成数据收集、异常处理、需求对齐和沉淀准入确认。
2. 再按本文执行 Excel 映射回填、评论生成和线上系统评论回刷。
3. 最后回到下一轮基准导出，验证线上系统是否已经沉淀结论。

如果回填动作执行中发现编号错误、对象不存在、依赖服务未确认、评论内容有争议，应立即停止该条记录的回填，并退回运作规范流程重新对齐。
